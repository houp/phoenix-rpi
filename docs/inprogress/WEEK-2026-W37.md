★★★ **PROVEN PORTING BUG FOUND — Mesa's GL path munmaps the WINSYS's own BO mapping** (mesa
`274ee5abea9`, unbuilt). `bo->map` is not a libc `mmap()` result on this port: the winsys hands out
its own `b->cpu` as the MMAP_BO offset. `v3d_bo_free()` `munmap`s it anyway, returning pages to the
kernel while `W.bos[slot]` still has `used=1`, a live `->cpu` and **valid GPU PTEs** — so malloc can
take the same pages for a heap. That is a concrete route for a 4-byte store to land on allocator
metadata.
ⓘ **Verified, not taken on trust:** the identical hazard is already guarded in **two of three**
places (`v3dv_bo_unmap`, `ioc_close_bo`) — the **GL path STK uses was missed**. And it silently
defeated the W36 winsys fix that stopped recycling a closed BO's address: `V3D_UNMAP_CLOSED_BO` is
set **nowhere**, so this was the ONLY path still returning BO pages to the kernel.
⚠ Sharper for imported BOs: the size is a caller-supplied `stride*height`, **not page aligned**, so
the munmap tore a partial hole out of the HEAD of a mapping the winsys still owned. Scanout BOs
bypass the BO cache and every RT ≥1024x768 is scanout ⇒ STK's deferred pipeline hit this constantly,
which also explains **why STK and not the GL1-style Quakes**.
★★★ **MEASURED — and it proves the mechanism AND kills my fix as written.** One 6-lap run,
3527 frames, `V3D_BO_TRACE=1`:
- **56 CPU addresses were reused across BO handles** on the CURRENT build, where `ioc_close_bo`
  deliberately does **not** unmap. Something frees them behind the winsys's back, and the only
  candidate left is Mesa's `v3d_bo_free()` munmap. ⇒ **W36 fixed the wrong side**: it disabled the
  winsys unmap to stop address recycling, but the recycling came from Mesa (5 reuses then, **56**
  now). A freed address can equally be taken by **malloc** — that is the corruption route.
