## 3. ★★★ TOP PRIORITY — `premain-hang`, a REGRESSION from the 2026-09-09 merge window

**~17% of cold app launches print nothing at all.** This is the single biggest demo risk, and on your
read (which the timeline supports) it is a regression, not an old bug:

| when | what |
|---|---|
| 2026-09-09 16:13 | last showcase video — system stable |
| 2026-09-09 14:49 / 19:03 | kernel `4ea46701` "8 → 64 priorities", merged `0c768551` |
| 2026-09-10 05:00 | **first silent-launch artifact in the whole repo** |

### ✅✅ ROLLBACK CONFIRMS IT — the fault is in the 2026-09-09 core window

| core tree | silent | clean |
|---|---|---|
| rolled back to **2026-09-09** (`restore-integration-state.sh`) | **0** | **26** |
| current | **8** | 36 |

**Fisher p = 0.0220.** Rolling the core back to the pre-merge state makes the fault disappear.
ⓘ Clean isolation on one axis: the **port binaries were NOT rolled back**, so `quakespasm` is
byte-identical in both arms — the difference is core only.
⚠ But the rollback moved the **whole** core window (kernel, libphoenix, corelibs, devices, usb,
project, utils, tests, posixsrv, filesystems), not just the priority merge — a kernel-only rollback
does **not build** (`PH_PRIO_DEFAULT`/`PH_GET_PRIO`, then `setPriority`, are ABI-coupled to
libphoenix and corelibs). So the culprit is *somewhere in that window*; the priority merge is the
suspect, not yet the proven cause.
⏭ **Next, per your method:** re-apply forward and retest each step. Cheapest first cut — move the
**kernel alone** forward to `0c768551` while the rest stays at 09-09 (old libphoenix does not use the
new macros, so that direction should build).

🐞 **Trap worth knowing: `restore-integration-state.sh` also moves the COORDINATION repo** (a
manifest's `_build` row is this repo), taking `scripts/` and `docs/` back with it. The first A/B run
silently degraded to plain boot captures because the `--stamp` support it was passed did not exist at
the restored SHA. Only tell: `-netboot-` in the log name. Warned in the script now.

**What is established:**
- ★★★ **The race is at the exec → user-mode hand-off.** One `lib_printf` immediately before the
  EL1→EL0 `eret` makes the fault vanish: **0 silent / 33 clean** with it, **8 / 36** without.
  **Fisher p = 0.0091.** The instrument suppresses what it was built to split, so "kernel-side vs
  crt0" is still open.
- ★★ **`DEBUG_THREADS` is defined NOWHERE**, so the scheduler's ready-list asserts are compiled out
  of every build we run — the 8→64 merge did that. Enabling it (new `KERNEL_DIAG` knob, kernel
  `a95189f9`/`5a273b0c`) found a real defect on the first run (§4).
- The scheduler **orphaned-queue** mechanism is real but **0 assert fires in 28 runs** ⇒ not the cause.
  The ready-bitmask arithmetic is **correct**; that hypothesis was wrong.
- ⛔ A watchdog in `proc_spawn()` is **dead code** for an app launch — psh uses **`vfork` + `execve`**.

**Next step, and a confound to respect.** The obvious A/B is to rebuild at kernel `137ec58f`
(pre-window) and re-run. ⚠ But a full tree restore also changes libphoenix, ports and the project,
which moves timing *a lot* — and this bug is now known to be timing-sensitive enough that one printf
hides it. A clean A/B result could therefore be a timing artifact rather than evidence about the
priority merge. So: prefer a **kernel-only** revert (check the `sys_priority` rename ABI against
current libphoenix first), and read any result with that confound stated.
⏭ Better still, a probe that does **not** add delay — record into a ring buffer and read it out
afterwards, instead of printing at the hand-off.
⏭ Look hard at **`vfork` + `execve`**: it shares stack and map between parent and child across
exactly this hand-off, and `6d8f40a5` / `20802d61` in the same window are both vfork stack/map
lifetime fixes.

## 4. 🐞 Deterministic defect, newly visible: `unlock on not locked lock`

`_proc_lockClear:2154 — lock: user.mutex, pid: 25, tid: 60, unlock on not locked lock` — QuakeSpasm
unlocks a userspace mutex that is **not locked**, **once in every run** (26 of 28), at **exit**.
Deterministic, so it needs code reading rather than trials. Root-cause analysis in progress; the open
question is whether it is a real double-unlock in libphoenix/the app, or a kernel bookkeeping bug
where `owner` is legitimately NULL for a held lock (which would make the assert a false alarm).
