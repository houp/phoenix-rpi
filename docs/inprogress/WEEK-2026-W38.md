## 3. ★★★ TOP PRIORITY — `premain-hang`, a REGRESSION from the 2026-09-09 merge window

**~17% of cold app launches print nothing at all.** This is the single biggest demo risk, and on your
read (which the timeline supports) it is a regression, not an old bug:

| when | what |
|---|---|
| 2026-09-09 16:13 | last showcase video — system stable |
| 2026-09-09 14:49 / 19:03 | kernel `4ea46701` "8 → 64 priorities", merged `0c768551` |
| 2026-09-10 05:00 | **first silent-launch artifact in the whole repo** |

### ✅✅ ROLLBACK CONFIRMS IT — the fault is in the 2026-09-09 core window

| core tree | silent | clean |
|---|---|---|
| rolled back to **2026-09-09** (`restore-integration-state.sh`) | **0** | **26** |
| current | **8** | 36 |

**Fisher p = 0.0220.** Rolling the core back to the pre-merge state makes the fault disappear.
ⓘ Clean isolation on one axis: the **port binaries were NOT rolled back**, so `quakespasm` is
byte-identical in both arms — the difference is core only.
⚠ But the rollback moved the **whole** core window (kernel, libphoenix, corelibs, devices, usb,
project, utils, tests, posixsrv, filesystems), not just the priority merge — a kernel-only rollback
does **not build** (`PH_PRIO_DEFAULT`/`PH_GET_PRIO`, then `setPriority`, are ABI-coupled to
libphoenix and corelibs). So the culprit is *somewhere in that window*; the priority merge is the
suspect, not yet the proven cause.
### Forward re-apply — a GRADIENT, not a single bad commit

| core state | silent | clean | rate |
|---|---|---|---|
| 2026-09-09 **pre** merge | 0 | 27 | 0% |
| 2026-09-09 **post** priority merge | 1 | 25 | 3.8% |
| **2026-09-12** | 3 | 22 | 12% |
| current | 8 | 36 | 18% |

The rate climbs steadily rather than stepping at one commit, so single-commit bisection is unlikely
to name a culprit. Treat the **exec → user-mode hand-off** lead (p = 0.0091 suppression) as primary.

### Forward re-apply, step 1 — the priority merge alone does NOT explain the rate

| core state | silent | clean | rate |
|---|---|---|---|
| 2026-09-09 **pre** merge | 0 | 27 | 0% |
| 2026-09-09 **post** priority merge (`0c768551`) | 1 | 25 | 3.8% |
| current | 8 | 36 | 18% |

pre vs current **p = 0.0205** (significant) · post-merge vs pre **p = 0.49** · post-merge vs current
**p ≈ 0.14**. ⇒ **The priority merge is NOT established as the cause.** One event in 26 is not
distinguishable from zero, and the large rate needs something that landed **after** 09-09 — or a
compounding of several changes.
⏭ **Next bisect point: the middle of 09-09 → 09-13** (the AF_UNIX kernel rewrite of 09-11, or the
09-12 malloc work). Bisect by integration manifest, not by single commits: the priority change is
**cross-repo atomic** (kernel + libphoenix + corelibs + usb all fail to build independently), so
single-repo steps do not compile.

🐞 **My own process error, recorded so it is not repeated:** I launched the second bench while the
first was still running — two cycles on one UART, which produces **0-byte logs** (the documented
one-cycle-at-a-time rule). My wait loop had timed out rather than observing the process exit, and I
read the score as final. Re-scored using only uncontended trials: the pre-merge arm is **0/27**, so
the conclusion held, but it could equally have destroyed the result. Wait loops must check that the
process actually exited.

🐞 **Trap worth knowing: `restore-integration-state.sh` also moves the COORDINATION repo** (a
manifest's `_build` row is this repo), taking `scripts/` and `docs/` back with it. The first A/B run
silently degraded to plain boot captures because the `--stamp` support it was passed did not exist at
the restored SHA. Only tell: `-netboot-` in the log name. Warned in the script now.

**What is established:**
- ★★★ **The race is at the exec → user-mode hand-off.** One `lib_printf` immediately before the
  EL1→EL0 `eret` makes the fault vanish: **0 silent / 33 clean** with it, **8 / 36** without.
  **Fisher p = 0.0091.** The instrument suppresses what it was built to split, so "kernel-side vs
  crt0" is still open.
- ★★ **`DEBUG_THREADS` is defined NOWHERE**, so the scheduler's ready-list asserts are compiled out
  of every build we run — the 8→64 merge did that. Enabling it (new `KERNEL_DIAG` knob, kernel
  `a95189f9`/`5a273b0c`) found a real defect on the first run (§4).
- The scheduler **orphaned-queue** mechanism is real but **0 assert fires in 28 runs** ⇒ not the cause.
  The ready-bitmask arithmetic is **correct**; that hypothesis was wrong.
- ⛔ A watchdog in `proc_spawn()` is **dead code** for an app launch — psh uses **`vfork` + `execve`**.

**Next step, and a confound to respect.** The obvious A/B is to rebuild at kernel `137ec58f`
(pre-window) and re-run. ⚠ But a full tree restore also changes libphoenix, ports and the project,
which moves timing *a lot* — and this bug is now known to be timing-sensitive enough that one printf
hides it. A clean A/B result could therefore be a timing artifact rather than evidence about the
priority merge. So: prefer a **kernel-only** revert (check the `sys_priority` rename ABI against
current libphoenix first), and read any result with that confound stated.
⏭ Better still, a probe that does **not** add delay — record into a ring buffer and read it out
afterwards, instead of printing at the hand-off.
❌ **`vfork` REFUTED as the cause (2026-09-14).** psh launches external commands via `psh_runfile()`,
which `vfork()`s and then — illegally for a vfork child — calls `getpid()`, `setpgid()`,
`tcsetpgrp()` (an **ioctl, i.e. a blocking IPC**) and `fprintf()` while sharing the suspended
parent's stack and map. That fits the symptom and the two vfork lifetime commits in the window, so I
tested it single-variable by switching that one call to `fork()`:

| psh launch path | silent | clean | rate |
|---|---|---|---|
| `vfork()` (shipped) | 8 | 36 | 18% |
| `fork()` | 1 | 25 | 4% |

**Fisher p = 0.139 — not significant, and the fault still occurred.** So the vfork window is not the
cause. ⚠ The ~4× apparent drop is also confounded: `fork()` is slower, and this bug is demonstrably
timing-sensitive (a single printf hides it). Experiment reverted; nothing shipped.
ⓘ Worth keeping as a separate cleanup regardless: those calls in a vfork child are undefined
behaviour and a latent hazard, independent of `premain-hang`.

## 4. 🐞 Deterministic defect, newly visible: `unlock on not locked lock`

`_proc_lockClear:2154 — lock: user.mutex, pid: 25, tid: 60, unlock on not locked lock` — QuakeSpasm
unlocks a userspace mutex that is **not locked**, **once in every run** (26 of 28), at **exit**.
Deterministic, so it needs code reading rather than trials. Root-cause analysis in progress; the open
question is whether it is a real double-unlock in libphoenix/the app, or a kernel bookkeeping bug
where `owner` is legitimately NULL for a held lock (which would make the assert a false alarm).

## 4b. ⚠ pthread_join "fix" was WRONG — pushed, then REVERTED (libphoenix `f9ad788`)

I pushed `8f1cc7f` (removing `pthread_join`'s trailing `mutexUnlock`) as verified. **It was not, and
it broke pthread.** Measured single-variable, same tree and kernel:

| libphoenix | `/bin/test-libc-pthread` |
|---|---|
| with `8f1cc7f` | **HANGS after 3 tests** (3 runs), 1 kernel lock assert |
| reverted | **28 Tests 0 Failures 0 Ignored**, 0 asserts |

So that unlock is **not** redundant: removing it leaves `pthread_list_lock` held and the next thread
operation deadlocks. The assert appeared to go away only because a stray unlock was replaced by
*never unlocking* — symptom suppressed, deadlock introduced. Reverted and pushed.

🐞 **How it got past me — a measurement error, again.** I verified with
`grep -c 'unlock on not locked lock'` and read 0. **The UART corrupts that string** (`unlock` →
`uplock`, and it interleaves mid-line with app output), so the grep scored 0 on a log that *did*
contain the assert. ⇒ **Score these by grepping `lockClear`, never the full sentence.** My "no second
site, withdrawn" note in the last update was a product of the same false negative and is itself
withdrawn.
⚠ Also: the QuakeSpasm arm looked clean for a real reason — quakespasm exits immediately after the
join, so a permanently-held lock has no observable consequence there. A 5-run green on one workload
did not generalise.

**What still stands:** the kernel genuinely reports `_proc_lockClear: unlock on not locked lock` once
per QuakeSpasm run. The *diagnosis* is withdrawn, not the observation.
⏭ Next: the likely source is `proc_lockWait()` (`proc/threads.c:2231`), which calls `_proc_lockClear`
on the same path — i.e. a `pthread_cond_wait` on a mutex the caller does not own — reached from
`proc_condWait` (`proc/cond.c:162`). That is a different mechanism from a stray `mutexUnlock`.
ⓘ Separately confirmed real and unfixed: `_pthread_release()` pushes onto `pthread_common.retired`
**after** the lock has been dropped (`pthread.c:417-435`), racing `_pthread_reapRetired()`; and
`pthread_create()` never initialises `ctx->exiting`.

✅ **Tree HW-verified after the revert**: unix-socket **38/0 `OK`**, pthread **28/0**, 0 faults,
quakespasm `Host_Init` **2.239 s**, no diagnostics in the loader.
Manifest `2026-09-14-pthread-fix-reverted-clean.md`.
