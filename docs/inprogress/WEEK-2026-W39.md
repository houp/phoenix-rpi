## 1. WHERE THINGS STAND — nothing is blocking, one call is yours

Everything is green and, for the first time, **green on the card as well as over the network**.

- **The SD card driver is done in both directions.** ADMA2 32-bit scatter-gather is the data path
  for reads *and* writes — the engine Linux runs on this silicon. The long-recorded "BCM2711
  DMA-write quirk" was **ours**: a raw CPU-physical address where the emmc2bus `dma-ranges` wants a
  bus address. Measured end-to-end (`/usr/bin/dd`, 64 MiB): PIO 12.2 · SDMA 12.3 · **ADMA2
  12.7–12.9 MB/s** — the SD bus bounds all three, so ADMA2's win is structural, not a rate.
- **The card now carries a current build** (devices `876e9605`, flashed 2026-09-20 **by the ADMA2
  write path itself**, 1.1 GB in 88.6 s). It is no longer the old `b95e983a` artifact, so the audio
  containment, the upstream sweep and every fix of the week are on it.
- **Six-app showcase gate 6/6 on the SD lane** (`sdrootgate`: x, qspasm 9369, q3 8480, q2 8431,
  vkq 6190, stk 1186 frames; torches present; 0 faults, 0 ADMA errors, 6/6 boots found both
  partitions) — every asset, font, shader blob and pak read off the card's ext2 root through ADMA2.
  And 6/6 on netboot (`fulldmagate`). Manifest `2026-09-20-w38-adma2-full.md`.
- **Flashing is autonomous and takes ~90 s.** The card never leaves the Pi: netboot Phoenix, `dd`
  the image from the NFS root onto `/dev/mmcblk0`, drop dnsmasq, power-cycle. Procedure kept in the

- **Public docs reconciled 2026-09-20** — README, `KNOWN-ISSUES.md`, the hardware-support matrix and
  `HARDWARE.md` all now say ADMA2-both-directions, and the stale "the `b95e983a` card predates the

## 1b. 2026-09-20 — a retraction, and the base-tool question it opened

↩ **The "busybox `dd` is 19× slower than coreutils" claim was mine and it is FALSE.** Measured A/B in
one boot (`ddbench`, 64 MiB, same source, same sink, both binaries): **5 s vs 5 s at `bs=1M`, 6 s vs
6 s at `bs=128k`**. The "28-minute flash" was **~25 min of `--idle-secs 1500` after `dd` had already
returned** — the identical harness artefact I had retracted three other numbers for hours earlier,
re-committed on the next variable. Fixed in the `rpi4-flash-sd` skill (which now also sizes
`--idle-secs` to the transfer), `docs/done/WEEK-2026-W38.md`, `docs/misc/2026-09-19-sdma-write-…`,
and memory. Surviving difference: coreutils `dd` self-reports a rate, this busybox build cannot
(`FEATURE_DD_THIRD_STATUS_LINE` off).

⏸ **Owner question (raised 2026-09-20): should busybox leave the base image?** The census:

- **`/bin` precedes `/usr/bin`**, so busybox **1.27.2 (2017)** shadows coreutils 9.5 for **22 names**
  — `base64 cat chmod cp date dd echo false kill link ln ls mkdir mv pwd rm rmdir sleep stat stty
  touch true`. A third layer exists: **psh resolves its own builtins before PATH**, so `ls` is psh's
  at `(psh)%`, busybox's under bash, and coreutils only by full path.
- **busybox is NOT load-bearing on Pi 4.** plo starts every driver from the syspage and
  `/etc/rc.psh` runs `bind`/`dummyfs`/`posixsrv`/`psh`. The busybox `/etc/rc` + `/etc/inittab` are
  unused ports-layer legacy, and **no script in `/bin`, `/sbin` or `/usr/bin` has a `#!/bin/sh`
  shebang**.
- It does uniquely supply **15 names**: `sh/ash, sed, grep/egrep/fgrep, tar, gzip/gunzip/zcat, vi,
  ed, login, usleep`. (`awk`, `find`, `xargs`, `diff`, `cmp` are already GNU in `/usr/bin`.)
- ⓘ **Not a problem, checked:** the 37 busybox names are hardlinks and the **SD image preserves
  them** (inode 15, `Links: 61`). No image bloat. Only the NFS *export* staging copy breaks them
  (~24 MB) — a host-side `rsync -aH` fix.

✅ **And the real reason coreutils looked inferior was our bug.** `dd: cannot fstat '/dev/mmcblk0':
Function not implemented` — `sdstorage_srv.c` handled `mtOpen/mtRead/mtWrite/mtGetAttr/mtMount` but
**not `mtStat`**, so every `stat()` of the card hit `default: -ENOSYS`. busybox worked only because
its `dd` does not stat first. Fixed (devices `a2b0c75` + include fix) — building, then gating.

⛔ **`scripts/syntax-check.sh` could not fail for the file you asked about.** `make -n <obj>` prints
the recipes for *every* prerequisite in that directory; the script took `grep -m1`, i.e. the **first**
gcc line, so requesting `sdstorage_srv.c` compiled **`sdcard.c`** instead and reported CLEAN for a
file the real build rejects. Found by running a negative control after the real build failed on the
error the check had passed. Now matches the compile line by source name and refuses to guess if the
match is not unique; verified in **both** directions plus a second repo.

## 1d. USB mass storage — bulk WORKS; mount is the open item

**★ OWNER GOAL (2026-09-20):** the SanDisk stick in the Pi fully usable — enumerate, block
device, mount, read+write, hot-plug/unplug — **and its read/write throughput MEASURED**. Work
autonomously (cron `a93931c8`, every 2 h).

✅ **xHCI bulk endpoints implemented and HW-PROVEN** (devices `3330b1d`). The HCD had grown one
scenario at a time and knew only control + interrupt-IN; bulk was not *refused*, it was
**unrepresented**, so `usb_open()` handed back a valid pipe the hardware had never configured and
every transfer failed on a healthy device. Added EP types 2/6, per-endpoint pipe storage (a slot
had ONE `interruptPriv`; mass storage needs bulk IN and OUT at once), and a submit path that
splits a buffer into physically contiguous runs — the interrupt path never needed that because its
buffers are a few bytes, but a kilobyte bulk buffer can straddle non-adjacent pages.
On HW: `xhci: bulk-OUT pipe ready slot=2 ep=4` / `bulk-IN … ep=3`, and
`umass: New USB Mass Storage device: /dev/umass0 sectors: 4194304` — exactly `PHXTEST1`, so the
MBR read and SCSI READ CAPACITY/READ(10) are all correct. Reads verified.

★ **The umass driver already existed upstream** (ia32-only) — wired up for aarch64, plus a
`-Werror=format` fix (`%lld` vs an `off_t` that is `long int` here, most likely why it stayed
ia32-only) and an `mtStat` handler.

🐞 **Three umass bugs found and fixed on the way:**
1. Hosted in-daemon, `ops.init()` gets NULL args and the NULL path set `mount_root = true` — it
   tried to mount the first stick anyone plugs in **as the system root**, contradicting the
   driver's own `-r` opt-in default.
2. `umass_mountFromDev()` set `part.fs` *before* attempting the mount and never cleared it on
   failure. `part.fs` **is** the "already mounted" flag, so one failed attempt made the device
   permanently unmountable, reporting `-EEXIST` — which reads as "busy", not "the first attempt
   failed".
3. `UMASS_MOUNT_EXT2` was gated on `$(filter ia32 aarch64,$(TARGET_FAMILY))`, and **TARGET_FAMILY
   here is `aarch64a72`** — the gate silently matched nothing.

✅✅ **THE STICK WORKS — mount, read and write, all HW-verified, 0 faults.**
`mount rc=0`, and graded **by content**: `sha256sum -c SHA256SUMS` → **5/5 OK, rc=0**, including
`big.bin` (17 MiB, well into the double-indirect region) and the 4-deep `deep/a/b/c/leaf.txt`.
Writes verified too: 8 MiB written and read back, plus a create/read/delete round-trip.
Manifest `2026-09-20-w39-usb-stick-working.md`.

🐞 **Two more umass/xhci bugs found getting there, each mis-pointing at the previous layer:**
4. `UMASS_MOUNT_EXT2` enabled the ext2 code but **nothing linked libext2 into the usb daemon** —
   `UMASS_LIBS` in umass's Makefile applies to the standalone binary, not to the
   `libusbdrv-umass.a` hosted in the daemon. Added `USB_HOSTDRV_DEP_LIBS` so a hosted driver can
   bring its own non-USB dependencies (usb `Makefile`, ordered after the driver because static
   archives resolve left to right).
5. ★ **umass silently truncated every I/O to its 4 KiB bounce buffer** and returned the truncated
   count as if it were the whole transfer. Measured: `512→512, 4096→4096, 8192→4096, 16384→4096`.
   libext2 reads more than 4 KiB while mounting, saw a short read, and reported **-EIO** — an error
   that points at the device rather than at the driver that shortened the request. Now loops at up
   to 64 KiB per SCSI command.

⚡ **Completion latency fixed — and the first attempt made it worse, which is the interesting part.**
Bulk completions now reaped by the submitting thread instead of the 1 ms roothub poll. The first
version left the poller polling bulk **too**, so both consumers raced for one event and the loser
blocked until its own timeout: every transfer became a multi-second stall, **slower than the poll it
replaced** (the test that had checksummed three files got through none). Fixed by giving each
endpoint type one owner — poller keeps interrupt-IN, the submitting thread owns bulk and must
therefore complete it on every path, including `-ETIMEDOUT`.

📊 **THROUGHPUT MEASURED — GOAL ITEM MET** (coreutils `dd`'s own reported rate, never harness
wall-clock; writes use `conv=fsync` so the flush is inside the number, and `cksum` verifies what
landed):

| path | before the poll fix | **after** |
|---|---|---|
| **raw `/dev/umass0`, bs=1M** | 14.7 MB/s | **29.3 MB/s** |
| raw, bs=64k | 14.5 MB/s | **28.2 MB/s** |
| raw, bs=4k | 1.3 MB/s | **8.1 MB/s** |
| **ext2 read** (17 MiB, `PHXTEST1`, 1 KiB blocks) | 320 kB/s | **3.0 MB/s** |
| **ext2 write** (16 MiB, `conv=fsync`) | 3.2 MB/s | **5.4 MB/s** |

**29.3 MB/s is essentially USB 2.0 High-Speed line rate** (the stick negotiated 480 Mbps behind the
Pi's hub). ⚡ The 2–6× jump came from one thing: `xhci_eventAwait` polled the event ring with a flat
`usleep(1000)` while the controller finishes a transfer in tens of microseconds. One SCSI command is
three transfers, so it cost ~3 ms per command — **fixed cost, not bandwidth**, which the raw
block-size sweep made unambiguous (4 KiB → 3.1 ms/command vs 64 KiB → 4.4 ms). Now 20 µs for the
first 4 ms, then back off.

↩ An earlier write figure of 3.1 MB/s was taken with a `sync` that had silently failed (psh's
`/bin/sync` needs a device argument) and could have been measuring cache. It happened to be close to
right, but it was not evidence when quoted.

⏭ **ext2 read is still 10× below the raw device**, and the cause is structural: umass has **no block
cache at all**, where `bcm2711-emmc` runs libcache with 128 KiB sectors. With 1 KiB ext2 blocks that
is ~17 400 SCSI commands for a 17 MiB file. Adding libcache is the next lever, well-precedented here.

🐞✅ **Hot-unplug of a MOUNTED stick was a use-after-free — fixed, but NOT hardware-tested.**
`_umass_devFree` freed the device struct while `umass_fsthr` was still blocked in `msgRecv` on a
stack **inside that struct**, never unmounted the filesystem and never destroyed the partition port.
Stopping the thread needed an explicit handshake, not just a `portDestroy`: it only ever left on
`mtUmount` and retried `msgRecv` forever on error. ⚠ Found by inspection — the stick cannot be
physically unplugged while the owner is away.

✅✅ **RELEASING A MOUNTED DEVICE NOW WORKS — full lifecycle proven on hardware.**
Three consecutive `mount → sha256sum -c → umount` cycles, all
`mount=0 sha256_rc=0 files_ok=5 umount=0`, then a **write round-trip across a umount**: a file and a
16 MiB `conv=fsync` write both survived umount+remount with a matching `cksum`. 0 faults.

★ **The hang was a self-deadlock, and it had two levels.** `umass_read`/`umass_write` take
`umass_common.lock`; the mtUmount handler held that lock across a synchronous `msgSend` whose
completion path runs `umass_poolthr → fs->unmount() → libext2 flush → umass_write()`. The driver
blocked against itself. Fixed by not holding the lock across the round-trip — and then the identical
bug was found one level up in `umass_handleDeletion`, which held it across `_umass_devFree`, so
**every unplug of a mounted stick would have deadlocked too**. That now unlinks under the lock and
tears down outside it.

ⓘ **The design was right all along and the machinery already existed** — `umass_poolthr` performs
the `fs->unmount()` and `umass_fsthr` exits on an `mtUmount` to its **own** port. libphoenix sends it
to the **device** port, so it only ever needed bridging. Two dead ends are recorded in the code so
they are not retried: `portDestroy()` cannot wake a thread blocked *inside* `msgRecv`, and
`_umass_partUnmount` must never be called holding `umass_common.lock`.

ⓘ Also fixed on the way, each a "server answers only the attribute its own code path needed" gap:
**`mtStat`**, **`atMode`** (umass *and* `bcm2711-emmc`), **`mtMountPoint`** + the mountpoint oid that
`mount()` passes and umass was discarding. ⚠ `umount` **by mountpoint** is still an unimplemented
TODO in libphoenix (`sys/mount.c:154` → `ENOTSUP`); only `umount /dev/umass0` works.

⚠ **Hot-plug/unplug remain physically untested** — the stick cannot be plugged or pulled while the
owner is away. The unplug path now shares the exact teardown proven through `umount()`, which is the
strongest evidence available without hands on the hardware.

✅ **MULTI-PARTITION WORKS.** `_umass_check()` took MBR entry 0 and discarded the rest; it now
walks all four and creates a node per non-empty one. `/dev/umass0` (`PHXTEST1`) and `/dev/umass1`
(`PHXDATA`) both appear and both mount, 5/5 checksums on umass0. A stick has one set of bulk pipes
and one CBW tag counter, so partitions share them through a new `dev->owner` and stay serialised;
only the owner destroys the lock. `mbr.h` gained `PENTRY_EMPTY`/`MBR_PARTITIONS`.
⏭ umass1's content check did not run in that cycle (the `[ -d ]` guard took the false branch) — re-run
it; the mount itself succeeded and listed `lost+found` + `phoenix`.

★★★ **OWNER GOAL (2026-09-20): max out transfer speed. ROOT CAUSE FOUND, fix REVERTED, bench
restored.**

**We were switching the USB 3 link off ourselves, every boot.** `PORTSC` bit 1 (PED) is **RW1CS —
writing 1 DISABLES the port** — and `SetPortFeature(PORT_POWER)` did `portsc | PP`, feeding a live
SuperSpeed port's own `PED=1` straight back at it:

```
probe:                   PORTSC=0x00281203  ccs=1 ped=1 speed=4 (SuperSpeed, U0)
SetPortFeature(1..5, 8)  <- PORT_POWER
GetPortStatus(2):        PORTSC=0x00000280  ccs=0
```

↩ **Fixed, measured, and REVERTED — because the fix alone makes the board worse.** With port 2
staying up, the stick correctly stopped presenting its USB 2 personality (a SuperSpeed device does
not use its USB 2 pins), port 1's reset came back **speed=1 with `Fail to get device descriptor`**,
and **nothing enumerated at all** — no hub, no stick, no keyboard, no mouse.

★ **The finding that matters: our USB 2 enumeration has only ever worked BECAUSE we were tearing the
SuperSpeed link down.** Every device reaches us through the VL805's USB 2 hub, which only happens
while the SS side is dead. **Half of USB 3 support is worse than none**, so the PORTSC fix must land
*together* with SS enumeration as one gated change: slot speed 4, route string to the SS root port,
ep0 = 512 (`bMaxPacketSize0` is an **exponent**, 9, not a byte count), and the SS Endpoint Companion
`bMaxBurst` into the endpoint context. ⚠ **Do not re-try the PORTSC fix on its own.**

✅ **Bench verified restored** after the revert: hub, SanDisk, `/dev/umass0` + `/dev/umass1`, mouse,
keyboard, 0 faults. Kept: the Supported Protocol / port-state diagnostic that made all of this
visible. Full detail: [`2026-09-20-usb3-superspeed-gap.md`](../misc/2026-09-20-usb3-superspeed-gap.md).

| | before | **after** |
|---|---|---|
| **ext2 read** (17 MiB, `PHXTEST1`) | 2.9 MB/s | **14.7 MB/s** |
| ext2 read, second pass (warm) | — | 14.8 MB/s |
| ext2 write (`conv=fsync`) | 5.4 MB/s | 4.6 MB/s |

ext2 read went from **10% of the raw device to 54%**. umass had no cache at all where
`bcm2711-emmc` has run libcache with 128 KiB sectors for years; each partition now gets a libcache

**WRITE_THROUGH deliberately** — this is removable media and a write-back cache would hold data a

partial lines and is the right trade. 0 faults.

⏭ The residual gap to raw is that libcache has no read-ahead: each new line is a separate blocking
64 KiB command with nothing overlapping it.

🐞✅ **`/dev/umass1`'s wrong contents ROOT-CAUSED: a 32-bit overflow in ext2, and it is not
USB-specific.** `ext2_block_read/write` computed the device offset as `bno * fs->blocksz` with both
operands `uint32_t`, so **the multiply wrapped at 4 GiB** before being widened to the `off_t` the
callback takes. Every ext2 filesystem over 4 GiB read and wrote the wrong place, silently.
The 2 GiB `PHXTEST1` was perfect because its highest offset is `0x80000000` — it just fits; the
27.5 GiB `PHXDATA` listed its root directory (low blocks) while a top-level directory in it would not
stat as a directory, the Orlov allocator having put that inode past the wrap. Fixed by casting before
multiplying (filesystems `ext2/block.c`). ⓘ **The SD card would hit this too** with a root over
4 GiB; today's is ~1 GB.

⏳ **umass1 still unverified — a NEW crash blocks it.** With the offset fix in, touching `/dev/umass1`
raises `Exception #32: Instruction Abort (EL0)`, `pc=far=0x46fa3c`, `esr=0x82000007` (level-3
translation fault on an **instruction** fetch), twice, with `/umass1` on the faulting stack. That is a
**userspace demand-paging** fault, not the driver's data path — the same family as the
`libc-uninit-main` / "page reads back zero" row in KNOWN-ISSUES, and the binaries live on NFS, not on
the stick. ⚠ `umass0` is completely unaffected (14.8 MB/s, 5/5 checksums), so the bench remains
usable; investigating this is its own track.

## 1f. 2026-09-21 — ✅ ROOT CAUSE FOUND AND FIXED: libext2 freed live inodes

🐞➡✅ **`_ext2_obj_create()` released an inode number it did not allocate.** It is called two ways:
with `inode == NULL` to allocate, and from `ext2_obj_get()` with an *existing* inode to pull it into
the object cache. In the second case `ino = pino` names a **live file**, but the error path ran
`free(inode); ext2_inode_destroy(fs, ino, mode);` unconditionally. Any failure in that block — the
`MAX_OBJECTS` (512) LRU eviction returning `-ENOENT` when every object is held, `malloc`,
`mutexCreate` — marked an in-use inode free.

The two inodes pulled into the cache most often are **root (2)** and **`lost+found` (11)** — exactly
the bits observed missing: group 0's inode bitmap read `0x000003fd` where a healthy filesystem reads
`0x000007ff`. Once inode 2 was free the allocator handed the **root directory** to the next
regular-file create, the object layer refused it, and **every** create returned `EINVAL` — while
`mkdir` still worked, because Orlov places directories in another group. One defect explains the
`lost+found` damage, the EINVAL, and the intermittency (it needs object-cache pressure).

Fix in `phoenix-rtos-filesystems` `ccd11e4`: release the number only when this call allocated it
(`free(inode)` stays unconditional — the object takes ownership on success). Also hardened
`ext2_inode_destroy()`, which rejected only inode 1, to refuse the whole reserved range 1..10;
`ext2_inode_sync()` deliberately untouched, since syncing root is legitimate.

✅ **HW-verified** on a freshly restored 1 GiB 4 KiB-block ext2. Before: every create `EINVAL`,
allocator printing `ino=2 bmp[0]=000003fd`. After: `touch`, shell redirect, `dd` and `mkdir` all
`rc=0`, allocator prints **`ino=12 bmp[0]=000007ff`**, `lost+found` still a directory, reference
`data.bin` sha256 unchanged (`c95413d29beacf15`).

↩ **Retraction 3 — "the EINVAL reproduces deterministically" was WRONG.** It was 1 reproduction in 2
valid runs; a third run was clean. It is pressure-dependent, which is consistent with the LRU

↩ **Retraction 4 — "heavy `umass0` traffic is required" was WRONG.** The EINVAL reproduced on a

## 1g. 2026-09-21 — ✅ SECOND ROOT CAUSE: every ext2 block > 1 KiB was off by one

🐞➡✅ **libext2 reserved bitmap bit N and handed the file block N+1.** A group's block bitmap is
indexed from the filesystem's **first data block**, which ext2 defines as **1 for 1 KiB blocks and 0
for every larger block size**. libext2's bitmap helpers take a 1-based bit index, and the block
number was computed as `group * groupBlocks + offset` — algebraically correct **only** when
`s_first_data_block == 1`.

Inside a free run this is invisible: each allocation reserves the previous block. **At the end of a
free run it hands out the first block of the next, USED run.** Group 0's free runs
(`585-623, 672-703, 896-1023, 1280-1535, 3072-…`) are each followed by a `data.bin` extent, so a
large write clobbered exactly **624, 704, 1024, 1536** — the first block of every extent, and
nothing else. That is why a 4 MiB and a 64 MiB write produced the *same* bad checksum.

`e2fsck -fn` on a pre-fix read-back is unambiguous:

```
Multiply-claimed block(s) in inode 12:     624 704 1024 1536   <- speed.bin
Multiply-claimed block(s) in inode 49154:  624 704 1024 1536   <- phoenix/data.bin
Block bitmap differences: -585 -672 -896 -1280 -3072 +19018
```

The `-585 -672 -896 -1280 -3072` are the first block of each **free** run: reserved, never handed
out. Both halves of the off-by-one, in one report.

**Scope: every ext2 with a block size above 1 KiB** — which is mke2fs's default for anything but a
tiny volume. It was never seen here because the SD rootfs is built `mke2fs -b 1024`
(`scripts/build-rpi4b-rootfs-ext2.sh`), so `fstBlock == 1` and the old arithmetic was accidentally
right. The USB stick was deliberately formatted with 4 KiB blocks, which is what exposed it.

Fix: one conversion pair (`ext2_blockToGroup` / `ext2_blockToOffs` / `ext2_blockFromOffs`) in
`block.c`, used by all six mapping sites including the free path. For `fstBlock == 1` they reduce
symbol-for-symbol to the old expressions, so **the SD lane is bit-for-bit unaffected**.

↩ **Retraction 5 — §1g's first version was wrong, and I had flagged the reason myself.** It said
"not the medium: the block bitmap is byte-identical and blocks 624..631 unchanged". Those dumps came
from the run whose **restore stopped at 255 MiB of 1 GiB without an error line**. On a full restore,
block 65 *does* change and 624 *is* zeroed. The `ext2_obj_t.ind[]`-cache hypothesis built on that
reading is dead — the indirect block was never corrupted; `data.bin`'s own data block was.

⚠ **Two tooling traps that produced those false readings**, both worth remembering:
`dd if=/dev/umass1 skip=<large>` fails with `cannot fstat` and leaves a **0-byte** file — check dump
sizes. And a restore can stop early while still printing a normal `copied` line — confirm
`1073741824 bytes`.

⏭ **Open:** anything Phoenix wrote to a >1 KiB ext2 *before* this fix carries a shifted bitmap —
`e2fsck` or reformat `umass0`/PHXDATA before trusting any measurement on them, or the next
"corruption" is a fossil.

## 1i. 2026-09-21 — ✅ THIRD root cause: unmount deleted the files it had cached

🐞➡✅ `libext2_unmount()` → `ext2_objs_destroy()` ran `_ext2_obj_destroy()` over **every** object left
in the tree, and that frees the **on-disk inode**; `ignoreSync` only suppresses the error it
returns. So every unmount marked free the inode of everything still cached — root, `lost+found`, and
anything touched since the mount. Invisible until the next mount, because the directory entries and
the data survive. `e2fsck` on a read-back of a filesystem that was merely mounted, written and
unmounted:

```
Inode bitmap differences:  +(11--13)
Free inodes count wrong for group #6 (8193, counted=8189)
Directories count wrong for group #6 (65535, counted=1)     <- unsigned underflow
```

**This is what turned `lost+found` into a 0-byte file** — the original symptom, three bugs ago. Fix
(`269306a`): release the in-memory object; free the inode only when `links == 0`, the
unlinked-while-open case. ⚠ **Not 4 KiB-specific** — `obj.c` has no block-size terms, so the 1 KiB SD
root is equally affected; it has not bitten there only because nothing unmounts that root, but
`ext2_objs_destroy()` is also the mount-failure cleanup path. ✅ Verified: `e2fsck` on a 1 GiB
read-back now reports **no inode-bitmap, no block-bitmap and no group-count errors**.

🐞➡ **Fourth, smaller: `i_blocks` was never maintained on the bulk write path.** `ext2_block_syncone()`
accounted for it, `ext2_block_sync()` (what `dd` and every buffered write use) did not, and indirect
blocks were not counted at all — so every file we created reported `i_blocks == 0` and `stat`/`du`
read 0 blocks. Both sites added; the truncate path already decremented correctly. In the cycle now.

## 2c. 2026-09-21 — 🐞➡✅ ELEVENTH ext2 defect: a hole read back the SUPERBLOCK

## 2d. 2026-09-21 — libphoenix line-buffering: a candidate bug, HELD until verified

Found while chasing why bash's `echo` is slow. bash's echo writes **`putchar()` per character**
(`builtins/echo.def:176`) and bash sets stdout line-buffered, so it is the exact shape that exercises
this path.

In `fwrite_unlocked()` the line-buffer flush — `memrchr(ptr, '\n', writesz)` then `write_data` — sits
**only in the `bufpos == 0` branch**. The "fill the incomplete buffer first" branch calls
`buffer_data()`, which is a bare `memcpy` with no newline check. So once the buffer is non-empty, a
`'\n'` is appended and **the line is not flushed**; it waits for the buffer to fill or an explicit
`fflush()`. C17 7.21.3p3 requires the flush.

⚠ **NOT COMMITTED, and here is why.** `phoenix-rtos-tests` already has
`TEST(stdio_bufs, setvbuf_linebuffer)` doing precisely `fputs("0123")` then `fputc('\n')` then
reading through a second descriptor — which is the pattern my reading says is broken. So either that
test is **currently failing** (and the fix makes it pass), or my reading is wrong and the change
should be dropped. Asserting a bug when an existing test contradicts it is how a plausible theory
gets committed as fact, which has already happened twice today.

⏭ Resolve by running the libc stdio suite on hardware and reading `setvbuf_linebuffer`'s CURRENT

## 2b. ⚠ 2026-09-21 — a 24x CLIFF between a 17-byte and a 513-byte file write

Measured while decomposing topic A (`A2v3`, counts asserted, `echo` builtin so no process spawn
per file):

| payload | 50 files | per file |
|---|---|---|
| 16 B (+newline = 17) | **13 s** | 260 ms |
| 512 B (+newline = 513) | **309 s** | **6180 ms** |

Both are **sub-block** writes taking the identical path in `_ext2_file_write()` — malloc 4 KiB,
`ext2_block_init`, memcpy, `ext2_block_syncone` — with **identical device traffic**. libext2's block
path therefore cannot explain it.

What does change at that boundary is the IPC message: `msg_t.i.raw` is **64 bytes**
(`phoenix-rtos-kernel/include/msg.h:115`), and `proc/msg.c:289` copies the payload inline when it
fits, else calls `msg_map()` (line 564) to map the sender's pages. 17 B fits; 513 B does not.

⚠ **Held as PROVISIONAL, and one observation already argues against the simple version:** 1 MiB `dd`
writes sustain **9.6 MB/s** through that same `msg_map` path, so "`msg_map` is slow" cannot be the
whole story — a 513 B write costing 6.2 s while a 1 MiB write costs ~0.1 s is not a per-message
mapping cost. Single sample, too.

### Mechanism read out of `msg_map()`, and a PREDICTION recorded before the measurement

`proc/msg.c:35` — for a payload that fits inside ONE page (`boffs != 0` and
`FLOOR(data) == FLOOR(data+size)`) the out-of-line path does, per message: reserve a page in the
destination map, **`vm_pageAlloc` a fresh physical page**, `vm_mmap` the source page into the kernel
map, two `page_map` calls, a `hal_memcpy`, then tear all of it down again. For a 1 MiB payload the
256 whole pages are mapped directly and only the two partial EDGE pages pay that cost — 2/258 of the
work instead of all of it.

**Prediction:** fast below the 64 B `raw` boundary, a step at it, then roughly **FLAT from 96 B to
512 B**, since every one of those is a single sub-page payload paying the same fixed setup. If
instead the cost rises smoothly across 64→512, this mechanism is wrong and the IPC story goes.

**dead** — and so is ext2's block path, which is O(1) in payload size, and the console (the payload
never appears in the UART log: 0 occurrences).

**The only shape that fits a per-BYTE cost is one message per byte.** Cross-check from A1: RAM was
5 ms for a 16 B file = **0.31 ms/byte** — also linear, just 40x cheaper. So the write path appears to
issue a message per byte, and each costs ~0.3 ms on dummyfs and ~12 ms on ext2/umass (where each one
is a read-modify-write of the block plus an inode sync plus a superblock sync).

⏳ `A2wr` in flight to confirm: the same 512 bytes written by `echo` (suspected per-byte), by
`dd bs=512 count=1` (a **single** `write()`), and by `cp` — plus a RAM control. If dd is ~12 ms where
echo is 6300 ms, the cost is the NUMBER OF WRITE CALLS, not the bytes, and the fix is buffering.

⏳ `A2bis2` in flight (16/48/64/96/128/256/512 B, 10 files each, from a clean restore) to test that.
