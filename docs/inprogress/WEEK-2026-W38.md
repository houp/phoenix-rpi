## 3. ⚠⚠ `premain-hang` — THE REGRESSION CLAIM IS WITHDRAWN, and the real rate is ~2%

**I compared instrumented builds against clean ones and called the difference a regression. That was
wrong.** Re-scored every arm from the logs, tagged by what instrumentation it carried:

| build arm | silent | trials | rate |
|---|---|---|---|
| 2026-09-09 rolled back (clean) | 0 | 27 | 0% |
| 2026-09-12 restored (clean) | 3 | 26 | 11.5% |
| **current, CLEAN (what ships)** | **1** | **52** | **1.9%** |
| current + `LIBC_STARTUP_TRACE=min` | 6 | 44 | 13.6% |
| current + exec-entry marker | 0 | 33 | 0% |

★★ **My diagnostic instrument raises the failure rate ~7×** (1/52 clean vs 6/44 traced,
**Fisher p = 0.045**). Every headline rate I have quoted — the "18% of launches", the
"cold+heavy 3.7%" — came off instrumented builds.
❌ **So the rollback result is void:** it compared rolled-back **clean** (0/27) against current
**instrumented** (6/44). Controlling for that, rolled-back clean vs current clean is **0/27 vs 1/52,
Fisher p = 1.00 — no difference whatsoever.** The 2026-09-09 window is **not** implicated by my data.
Witold's regression hypothesis is neither confirmed nor refuted; my evidence simply did not test it.
ⓘ The one arm that still looks odd is 09-12 clean (3/26) against current clean (1/52), p = 0.11 —
suggestive of nothing at this sample size.

★ **What this means for the demo (the standing goal): the risk is much smaller than reported.** On
the build that actually ships, a cold app launch fails to start about **1 in 52**, not 1 in 6, and
the workaround (relaunch) is unchanged. This does not need to block a recording.

⏭ **Method rule going forward:** never compare a rate across builds that differ in instrumentation.
Measure the clean build, or instrument both arms identically.
⏭ The defect is real and still open — it did occur once in 52 clean runs — but at ~2% it needs a
reproducer that does not perturb it, and every instrument I have tried either raises the rate (the
libc trace) or suppresses it (the exec marker). That, not more benching, is the blocker.
ⓘ Live fact worth keeping: the board stays **fully alive on the network** through the 300 s hang
(156 consecutive pings), so it is a localised process hang, not a console or scheduler wedge.

## 4b. `unlock on not locked lock` — narrowed: it is a real stray unlock, NOT the cond-wait path

`_proc_lockClear()` prints that line from **two** places: the `mutexUnlock()` syscall, and
`proc_lockWait()` — a condition wait on a mutex the caller does not own, which then returns `-EPERM`
**without waiting and without re-acquiring**. Same text, very different bugs, so the report alone was
not actionable. Added a distinguishing `LOCKWAIT-UNOWNED` marker (kernel `3be6f38c`, gated on
`DEBUG_THREADS`, pushed).

**Result: QuakeSpasm's once-per-run report shows 1 `lockClear` and 0 `LOCKWAIT-UNOWNED`** ⇒ it is a
genuine **stray `mutexUnlock` from userspace**, and the condition-wait hypothesis — the previous
leading candidate — is **refuted**.
⚠ Note this is *not* `pthread_join`: the fix I tried there was wrong and was reverted (it removed a
necessary unlock and deadlocked the pthread suite). The caller is still unidentified; `user.mutex` is
the generic name for every userspace mutex, so it could be any of them. It fires during exit, in
SDL's audio teardown.
⏭ To pin the caller, report `mutexUnlock()`'s `-EPERM` return with `__builtin_return_address(0)` from
libphoenix and map it with addr2line — the kernel knows the tid but not the userspace PC.
ⓘ Priority: **low**. It is benign while uncontended and happens at process exit, so it does not
affect the demo. Recorded so the next person does not re-run the same two dead hypotheses.
