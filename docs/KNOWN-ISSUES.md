# Known open issues

Every issue we know about and have **not** fixed, in one list. Nothing else.

- **Open only.** A fixed issue leaves this file. Closed rows are kept, verbatim, in
  [`done/closed-issues-archive.md`](done/closed-issues-archive.md) so nothing is re-litigated.
- **No decisions recorded here.** Fix / postpone / won't-fix is the owner's call, made from this
  list; earlier verdicts have been stripped deliberately.
- **No history.** Each row says what is wrong and what we last measured. Analyses live in
  `docs/misc/` and `docs/done/`.
- Open `TD-NN` transitional-debt items are issues too and are listed here.
  [`TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md`](TEMPORARY-FIXES-AND-FUTURE-CLEANUP.md) keeps their
  engineering detail; anything marked RESOLVED there is not repeated here.

Verified against the tree, the git history and the boot-log archive on **2026-09-22**. Where a
row's old claim turned out to be stale, the correction is noted in the row.

## 1. Correctness — crashes and data loss

| # | Issue | Last measured |
|---|---|---|
| C1 | **A stray four-byte write corrupts the high half of one heap header field, and every later `free()` from that heap then leaks.** `heap->size` sits at offset 0 of a page-aligned heap; the low 32 bits survive intact and only the high half is wrong, so the write lands at `heap+4`. Masked, both observed heaps are entirely self-consistent — legal `0xd000` size, chunks inside it, ordinary grid. ★ The corrupting word is **not constant** (`0x80000000` and `0x80000001` on two heaps in one run), which reads like a refcount or lock word with a flag in the MSB rather than a marker. Guards: `free() of a corrupt chunk header`, `large-bin lookup returned a non-chunk` / `a wild pointer`, `chunk handed out twice`. | **Live but rare, and a distinct signature from the historical bulk.** Archive-wide `hsize` is printed 24 231 times: 24 226 sane (`0x2000`) and **5 corrupt** — all 5 in one run (`gate-stk`, 2026-09-22, `why=5`, 0 faults, 1189 frames, still passed visually). Every high-count log predates the 2026-09-12 BO-ownership fix, so the pre-fix bulk was a bad chunk in a good heap and this residue is a good chunk in a bad heap. Next occurrence is instrumented to decide it — `hlo32` / `hhi32` / `hfixed`, and since 2026-09-23 from **every** reporter that prints a heap size, not just the corrupt-header one, so whichever guard fires first is decisive. The instrument is itself verified against an injected reproduction of the exact field state (`tools/malloc-harness`, `hi32-write`). ⛔ Do not re-walk the eliminated set: double BO ownership (measured clean, 0 overlapping reuses in 2 827 events), application overrun, or naming the `operator delete` caller (`-fomit-frame-pointer` makes it impossible). |
| C3 | **Two libc globals read back zero, killing the process at `main`.** `stderr` and psh's applet list are both unset, so `fprintf` dereferences a NULL `FILE*` (`far=0x30`). Both live in one 4 KiB `.bss` page. A source review gave a clean negative on every kernel mapping path, so "those writes definitely execute" is the assumption the next occurrence has to test. | **2 sightings (2026-09-07, 2026-09-15), none since.** Impact limited to `ntpclient`, which only sets the clock. The label added to make a recurrence self-explaining (`applet list is empty`) has **never fired** in the whole archive. |
| C4 | **Intermittent V3D binner wedge on long GPU runs.** Auto-recovered by a GPU reset that reports loudly (`RENDER TIMEOUT` / `DROPPED job`). Not an MMU fault — a CT0 front-end stall with zero error status, `ct0ca` parked inside a valid BCL BO. `q3dm7` is the documented reproducer. | **Not reproduced since 2026-09-09** (and that was an experiment-labelled run; last sighting on a shipping build 2026-08-22). 0 wedge signatures in every log 09-10 → 09-22, including 15 Quake III runs and both six-app gates. Diagnostics are armed, so the next occurrence self-explains. |
| C5 | **PWM audio DMA stalls at startup on some boots**, which used to hang Quake II inside `SDL_OpenAudio()`. Captured three times: the channel is alive but parked for a DREQ that never comes, ring full, 0 samples moved. Mechanism open. Blast radius is contained — the driver now grades the channel by progress, re-arms, and degrades to a paced null sink. | **Mechanism unfixed; symptom quiet.** 25/25 Quake II runs since 2026-09-18 reached `SDL audio initialized` and drew frames; 0 stall aborts in any log 09-19 → 09-22. ⚠ Timing-sensitive: the rate has moved across functionally neutral relinks, so short clean runs bound it rather than clear it. |
| C6 | **psh forks `ntpclient` fire-and-forget on session start**, so a ~56-year wall-clock step can land anywhere in a ~2-minute window. Any app that measures a duration in *wall-clock* time across its own startup sees nonsense. | **The one app that ever failed this way is fixed; the systemic exposure remains.** ✅ quake3's `Sys_Milliseconds` now uses `CLOCK_MONOTONIC` (`ports fd34552`) — it was the only port glue still using `gettimeofday`; quakespasm, vkquake and sdl2 already used monotonic. The property is measured, not assumed: `tools/clockstep` steps the wall clock 56 years on hardware and monotonic moves by exactly the `sleep(1)` (`mono-delta 1000 ms` vs `real-delta 1766015999858 ms`). ⏸ Still open and owner-gated: making psh *wait* for the clock is what its comment says was tried and reverted, and a bounded wait delays the prompt on every cold boot on every target since `pshapp.c` is shared. Historical rate of a visible failure: ~1 in 174 quake3 runs. |
| C8 | **A name on the NFS root intermittently stops resolving for a few operations, then starts again.** On 2026-09-23 three consecutive cases in the libc `stat_nlink_size_blk_tim` group each failed at their **first** resolution of the same relative path by name — `stat()`, `truncate()` and `lstat()`, all `Expected 0 Was -1` — while the two cases in between that touch a *different* name passed, and the group recovered by `st_dev_ino`. The file is created by the group's `TEST_SETUP` immediately after four `remove()` calls. | **~1%, and NOT a regression** — 1 firing in 90 archived runs of the group (89 of them on the netboot NFS root); the same binary then passed 212/0 **twice** on the next boot. The earlier "regression since 2026-09-22" reading was a 1-vs-1 comparison against a single archived run and is withdrawn. **Two** nfs-fs mechanisms are eliminated **by reading**: the attribute cache is positive-only (`fe3979d`), so it cannot hide a file that exists, and `nfs_node_detachPath()` unbinds the name, so a detached node cannot shadow a fresh lookup. A **third is open** — `nfs_ops_unlink()` does drop a cached node for the path, but only *after* a `nfs_lstat64()` that, on **any** failure including a transient RPC error, returns `-ENOENT` at `nfs_ops.c:1206` and never reaches that code. The group's `TEST_SETUP` calls `remove()` on three names that are expected not to exist, so it takes that early return every time; whether a node bound to the path can survive it with a lazily-cached `fh` (the idle LRU keeps one at `refs==0`) is unread and is the next thing to check. Since 2026-09-23 the next firing is self-explaining: the setup's `open()` is asserted with its errno, and the failing case reports whether `fstat()` on that same descriptor still works — `fd` valid + `fstat` OK + by-name `ENOENT` would mean the inode is fine and the **name** is what went missing, the only outcome that points back into nfs-fs. Instrument verified against real syscalls on the host, both failure shapes and the healthy one. |

## 2. Graphics and UI

| # | Issue | Last measured |
|---|---|---|
| G1 | **Windowed GL in X11 is bandwidth-bound, ~10 fps.** A GL app drawing into a window copies pixels GPU → CPU → socket → CPU → GPU every frame: 96 ms/frame at 640×480, of which `XPutImage` is 58 ms. No DRI3/DMA-BUF equivalent exists, so a client can only hand the server pixels, never a buffer reference. Full-screen GL is unaffected (the games bypass X). | Architectural. All cheaper mitigations measured and closed; a point fix was half-proven on hardware with a ceiling of only ~1.7×. |
| G2 | **xterm resize artefacts while dragging** on the GPU X desktop (owner-reported). | **Unreproduced.** No new evidence since 2026-09-14; resize *correctness* is verified once settled. The missing measurement is a deliberate drag test with the mouse released. |
| G3 | **A stale Mesa shader-cache blob renders as green speckle** over an otherwise-valid frame. Phoenix has no ELF build-id, so the cache keys on shader source only and a host toolchain change invalidates nothing. | **Mitigated, mechanism intact.** Both invalidation controls verified present 2026-09-22, and the `rsync --delete` hole that made the host-side one inert was closed 2026-09-16. No speckle report since. ⚠ The SD image ships **no** warm cache, so the first GL app on a freshly flashed card pays the full recompile. |

## 3. Platform limitations

| # | Issue | Last measured |
|---|---|---|
| P1 | **Only the 4 GB Pi 4B is validated, and 2/8 GB boards are known to be mis-mapped** — plo's syspage memory map is still hardcoded. The DTB parser also assumes a single interrupt controller. (TD-06, TD-15 remainder) | Open. Do not simply try an 8 GB board. Also in TD-15: VC4 quiesce + mailbox-move (low value), and drivers use identity va2pa (⚠ do not naively wire `dtb_armToBus` — it would break GENET). |
| P2 | **Asynchronous SError is masked in early kernel paths** because a live PCIe/VL805 USB external-abort SError is not root-caused; unmasking regresses boot. A dump-and-halt handler is implemented and armed. ⚠ This is why an MMIO read of an unclocked block **hangs silently** instead of aborting. (TD-10) | Open, HW-gated. |
| P3 | **`dc zva` fast path disabled in `hal_memset` on the Cortex-A72**, pending proof of the EL2 DC-ZVA trap state (does not reproduce in QEMU). Performance-only, correctness-safe. (TD-20) | Open, HW-gated. |
| P4 | **The generic aarch64 early-console path hardcodes the UART at VA `0xffffffffffe00000`**, because it must print before the DTB-discovered base is available. On the Pi 4B this alias equals the discovered pl011 base. Matters only when porting to another aarch64 board. | Open for a future cross-board port; inert on this board. |
| P5 | **Netboot NFS-root: one narrow boot-order race.** plo launches psh as a sibling of the NFS takeover without gating on it, so a command issued at the prompt can still hit the pre-takeover RAM root and report `not found`. The clean fix is a plo boot-order gate. | Open; invisible in practice because the test harness waits for the takeover marker. Confirmed still ungated in `user.plo.yaml` on 2026-09-22. |
| P6 | **`echo > file` from a shell script is ~50× slower than it should be on real storage.** bash's builtin output reaches the filesystem in very small writes, so cost scales with byte count: 5000 ms/file vs 100 ms for `cp` or `dd` on the same 512 bytes. Invisible on a RAM filesystem. | Open, ports-level (bash output buffering). The filesystem is not at fault. Workaround: prefer `cp`/`dd` or one redirect of a whole command's output. |

## 5. Debt and cleanup

| # | Issue | Last measured |
|---|---|---|
| D1 | **`RPI4AUDIO_ARMTRIALS` is a permanent diagnostic ABI in a published header** — an ioctl plus struct in `rpi4-audio.h` for a facility that can block the driver's only message thread. (TD-23) | Open by design; removal was tied to C6 closing, which has not happened. Still present at `rpi4-audio.h:65`. |
| D2 | **Three TD-14 fallbacks still soften Pi-4 boot, and the slowness they were written for is gone.** All three say "restore the fatal path once the underlying IPC slowness is rooted out": `pl011-tty.c:1271` treats `/dev/tty0` registration failure as non-fatal; `pl011-tty.c:1290` keeps an extra `portRegister()` alias for `/dev/console` beside `create_dev()`; `pshapp.c:1701` lets psh continue on inherited stdio when `/dev/console` cannot be opened (upstream does `return err`). ↩ *Corrected 2026-09-23:* the registry also listed a fourth ID, `TD-14-psh-ttyopen-errno`, as separately active — it has **no marker in source**; what it described is the errno print at `pshapp.c:1710`, part of the third item. | D3 | **SuperTuxKart still carries its own wide-printf shim**, because Irrlicht passes `wchar_t*` to `%s` — which the standard defines as a **multibyte** string (`%ls` is the wide one). ✅ *Half of this closed 2026-09-23: libphoenix now implements conforming `swprintf`/`vswprintf`* (`libphoenix 07a0a29`, 11 target tests in `test-libc-printf`), so any other port needing wide formatted output just works. | Open, and narrower than before. So any exception inside the bootloader gives a single letter instead of a register dump. | **Open; root cause identified 2026-09-23, fix is not a small edit.** The real dispatcher exists (`hal/aarch64/_exceptions.S:24`) but reads `spsr_el3` / `elr_el3` / `esr_el3` / `far_el3`, while that one table is installed at **three** exception levels — so at EL1 those EL3-only accesses trap and the crash gets worse, which is exactly why the tag table replaced it. Closing it means making the dispatcher `CurrentEL`-aware, or installing one table per EL. ⚠ Bootloader boot path, and plo takes no exception on a healthy boot, so this is diagnosability and upstreamability rather than correctness — the project's "attended" class.
