## 3. ⚠⚠ `premain-hang` — THE REGRESSION CLAIM IS WITHDRAWN, and the real rate is ~2%

**I compared instrumented builds against clean ones and called the difference a regression. That was
wrong.** Re-scored every arm from the logs, tagged by what instrumentation it carried:

| build arm | silent | trials | rate |
|---|---|---|---|
| 2026-09-09 rolled back (clean) | 0 | 27 | 0% |
| 2026-09-12 restored (clean) | 3 | 26 | 11.5% |
| **current, CLEAN (what ships)** | **1** | **52** | **1.9%** |
| current + `LIBC_STARTUP_TRACE=min` | 6 | 44 | 13.6% |
| current + exec-entry marker | 0 | 33 | 0% |

★★ **My diagnostic instrument raises the failure rate ~7×** (1/52 clean vs 6/44 traced,
**Fisher p = 0.045**). Every headline rate I have quoted — the "18% of launches", the
"cold+heavy 3.7%" — came off instrumented builds.
❌ **So the rollback result is void:** it compared rolled-back **clean** (0/27) against current
**instrumented** (6/44). Controlling for that, rolled-back clean vs current clean is **0/27 vs 1/52,
Fisher p = 1.00 — no difference whatsoever.** The 2026-09-09 window is **not** implicated by my data.
Witold's regression hypothesis is neither confirmed nor refuted; my evidence simply did not test it.
ⓘ The one arm that still looks odd is 09-12 clean (3/26) against current clean (1/52), p = 0.11 —
suggestive of nothing at this sample size.

★ **What this means for the demo (the standing goal): the risk is much smaller than reported.** On
the build that actually ships, a cold app launch fails to start about **1 in 52**, not 1 in 6, and
the workaround (relaunch) is unchanged. This does not need to block a recording.

⏭ **Method rule going forward:** never compare a rate across builds that differ in instrumentation.
Measure the clean build, or instrument both arms identically.
⏭ The defect is real and still open — it did occur once in 52 clean runs — but at ~2% it needs a
reproducer that does not perturb it, and every instrument I have tried either raises the rate (the
libc trace) or suppresses it (the exec marker). That, not more benching, is the blocker.
ⓘ Live fact worth keeping: the board stays **fully alive on the network** through the 300 s hang
(156 consecutive pings), so it is a localised process hang, not a console or scheduler wedge.

## 4b. ⚠ pthread_join "fix" was WRONG — pushed, then REVERTED (libphoenix `f9ad788`)

I pushed `8f1cc7f` (removing `pthread_join`'s trailing `mutexUnlock`) as verified. **It was not, and
it broke pthread.** Measured single-variable, same tree and kernel:

| libphoenix | `/bin/test-libc-pthread` |
|---|---|
| with `8f1cc7f` | **HANGS after 3 tests** (3 runs), 1 kernel lock assert |
| reverted | **28 Tests 0 Failures 0 Ignored**, 0 asserts |

So that unlock is **not** redundant: removing it leaves `pthread_list_lock` held and the next thread
operation deadlocks. The assert appeared to go away only because a stray unlock was replaced by
*never unlocking* — symptom suppressed, deadlock introduced. Reverted and pushed.

🐞 **How it got past me — a measurement error, again.** I verified with
`grep -c 'unlock on not locked lock'` and read 0. **The UART corrupts that string** (`unlock` →
`uplock`, and it interleaves mid-line with app output), so the grep scored 0 on a log that *did*
contain the assert. ⇒ **Score these by grepping `lockClear`, never the full sentence.** My "no second
site, withdrawn" note in the last update was a product of the same false negative and is itself
withdrawn.
⚠ Also: the QuakeSpasm arm looked clean for a real reason — quakespasm exits immediately after the
join, so a permanently-held lock has no observable consequence there. A 5-run green on one workload
did not generalise.

**What still stands:** the kernel genuinely reports `_proc_lockClear: unlock on not locked lock` once
per QuakeSpasm run. The *diagnosis* is withdrawn, not the observation.
⏭ Next: the likely source is `proc_lockWait()` (`proc/threads.c:2231`), which calls `_proc_lockClear`
on the same path — i.e. a `pthread_cond_wait` on a mutex the caller does not own — reached from
`proc_condWait` (`proc/cond.c:162`). That is a different mechanism from a stray `mutexUnlock`.
ⓘ Separately confirmed real and unfixed: `_pthread_release()` pushes onto `pthread_common.retired`
**after** the lock has been dropped (`pthread.c:417-435`), racing `_pthread_reapRetired()`; and
`pthread_create()` never initialises `ctx->exiting`.

✅ **Tree HW-verified after the revert**: unix-socket **38/0 `OK`**, pthread **28/0**, 0 faults,
quakespasm `Host_Init` **2.239 s**, no diagnostics in the loader.
Manifest `2026-09-14-pthread-fix-reverted-clean.md`.
