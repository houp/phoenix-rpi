## 3. ✅✅✅ `premain-hang` — ROOT-CAUSED AND FIXED (2026-09-15)

**`socket()` deadlocks the process that owns `/`.** The kernel (`posix/inet.c socksrvcall`) and
libphoenix (`sys/socket.c socksrvcall`, reached via `getaddrinfo`) resolved `/dev/netsocket` with a
**path lookup on every call**. A path lookup is answered by the filesystem that owns `/` — which
`nfs-fs` **is**, and it is **single-threaded** — so its own loop thread sent the lookup to the port it
was supposed to be servicing. Nothing ever answers it. libnfs opens a fresh socket the moment it must
reconnect, so a dropped server stopped the whole filesystem and every process blocked on its first
request. A launch hung while opening its own binary: that is the whole of `premain-hang`.

⇒ It was never crt0, libc, exec, `vfork` or the scheduler. Each of those was eliminated **correctly**
— the launched process was a victim.

| commit | what |
|---|---|
| kernel `7c021702` | cache the resolved oid in `posix/inet.c` |
| libphoenix `47dde32` | same in `sys/socket.c` — the `getaddrinfo` door; without it the reclaim stalls in `nfs_mount` |
| ports `a44623a` | libnfs patch 04: an overall deadline for a sync call. Defence in depth, **not** the cause — `rpc->timeout` is per-PDU and `rpc_timeout_scan()` requeues rather than fails, which is why `nfs_set_timeout(5000)` never bounded anything |
| filesystems `427aabd`, `d5db203` | reclaim on `-ETIMEDOUT`; watchdog re-reports instead of firing once |

**Gate (new): `./scripts/test-nfs-recovery.sh`** — restarts the host's nfsd under a running Pi and
requires the reclaim to complete AND a fresh process to launch afterwards, exiting non-zero otherwise.
On the clean build (zero diagnostic markers in the image):
`noticed=1 reclaimed=1 launched=1 wedged=0 faults=0 → PASS`, with quakespasm at `Host_Init` 2.24 s.
The same scenario wedged **2/2** before the fix. Manifest `manifests/2026-09-15-premain-hang-fixed.md`.

**Regression question, precisely.** The per-call lookup is **old** — not from the recent
kernel/libphoenix merges. Two of our own earlier changes made it reachable and then periodic: the
NFS-root takeover (`05f049a`, 2026-06-28) made `nfs-fs` own `/`, and the NFSv4 lease keepalive
(`8231627` + libnfs patch 01, 2026-08-03) put a synchronous RPC on the loop thread every 45 s. Before
that only an OPEN could force a reconnect, so the wedge was rare. ⇒ **an old latent defect, exposed by
NFS-root and turned from rare into periodic on 2026-08-03.**

ⓘ **Netboot/nfsroot only** — the SD demo image has an ext2 root and no `nfs-fs`, so it cannot hit
this. Every `premain-hang` observation came from a netboot cycle.
ⓘ **Method** (the one the owner asked for, not a pass-rate bench): a `volatile` mark set at each step,
read out by a watchdog thread re-reporting every ~10 s. Four refinements — `mark=5` (pre-`nfs_service`)
→ `31` (pre-`rpc_connect_sockaddr_async`) → `35` (**pre-`socket()`**) — frozen for 80 s.
ⓘ Full hunt, incl. the withdrawn rate/regression claims: [`docs/done/2026-09-15-premain-hang-hunt.md`](../done/2026-09-15-premain-hang-hunt.md).
### 3b. Same defect, second place — `/dev/posix/pipes` (kernel `4e473590`)

`pipe()`, `mkfifo()` **and `open()`** each resolved `/dev/posix/pipes` by path on every call. Same
deadlock shape, and `open()` paid for it on the hot path: the path is a devfs node, not a registered
port name, so it misses the kernel dcache and walks the namespace for real — **two extra `mtLookup`
messages per `open()`**, the first queued behind the same single-threaded server about to handle the
open. Cached the same way (success only — posixsrv may start later).
ⓘ Not a latency win in practice: `Host_Init` 2.231 s vs 2.239 s. The cost was queue pressure on
`nfs-fs`, not network time.
ⓘ Remaining instance of the pattern, low value: libphoenix `stdio/file.c` `tmpfile()`
(`/dev/posix/tmpfile`). Only bites a process that owns `/` and calls `tmpfile()`.

## 3d. STK crash hunt — two dead ends CLOSED, aim moved to the allocator (2026-09-15)

A source review of `FontWithFace::render` and everything it calls settles two things I had been
treating as live:

- ⛔ **Patch 0019 cannot have fixed `stk-highbits-pointer`.** The faulting `ldrb` is
  `font_with_face.cpp:787`, in the **collect** loop (630-805); 0019 patches loops starting at **834**.
  So the 11 clean STK runs since `b5ce28f` are **not** evidence (and are only p ≈ 0.31 anyway).
- ⛔ **There is no out-of-bounds 4-byte store anywhere in the render path** — every indexed store
  checked and in bounds; `grab()/drop()` write an 8-aligned refcount, not "8-aligned **+4**". And the
  `m_cached_gls` dangling-reference theory has **no invalidation path at all** (no `erase`, no
  re-entry into `getCachedLayouts`).

⇒ If a font-path store produced signature A, the store was *legitimate and the buffer was wrong*:
**the allocator handed the same memory to two owners.** Same root cause as `freebin-corruption`; the
fix belongs in the allocator/VM, not in STK.
⚠ Two published claims corrected: patch 0019's header is wrong that `getTexture()` returns a wild
pointer (it is bounds-checked and returns 0), and the "RGBA8 pixel" reading of `0x80000001` is
**unconfirmed** (`SColor(alpha=128,0,0,0)` is `0x80000000`; nothing yields `b=1`).
★ Kept from the review: `m_cached_gls` is never cleared in `GAME` state while HUD strings change every
frame, so it **grows unbounded for a whole race** — real per-frame heap churn, and a plausible reason
STK and not the Quakes is where the allocator bug surfaces.

**12-run STK soak on the current build: 12/12 started, 12/12 ZERO faults**, ~1850–2000 frames each
(`stksoak-T1..T12`). With the 11 earlier post-fix runs that is **23 STK runs since 2026-09-12 with 0
faults** — p ≈ 0.09 against the old ~1-in-10 rate, so **suggestive, not significant**, and per the
review above the font fix cannot be the reason. **Do not close it.**
ⓘ Two *contained* allocator events in the 23 (`hbase?=0`, large-bin lookup dropped, run continued).
ⓘ **1 run in 12 spent the whole 300 s window compiling shaders** (19 frames vs ~1850), with the Mesa
disk cache reported present for every trial — so a cold GPU start is intermittent, not just
first-run. Relevant to a live demo: warm each app twice, not once.

**Shipped so the next occurrence is decisive** (ports `d7a3740`): `0020` re-reads the bad
`{_M_start,_M_finish}` pair through a **`volatile`** pointer (a plain re-read is optimised away) and

## 3e. `libc-uninit-main` — new row, one sighting, no demo impact

The "ntpclient Data Abort, stack-overflow shape" reading was **wrong**. Exact: `far=0x30`,
`esr=0x92000007` (read), `pc` → `mutexLock(stream->lock)` in `fwrite`, libphoenix `stdio/file.c:777`;
`0x30` is `FILE.lock`, so the stream was **NULL**. The stack dump carries the formatted string
verbatim — `psh: ntpclient: unknown command` — i.e. `psh.c:211` `fprintf(stderr, ...)`. So **two**
globals were unset at once: `stderr` (set only in `_file_init`) and psh's applet list (filled only by
`__attribute__((constructor))`, one of which is `ntpclient` itself). ⇒ that process reached `main()`
with **libphoenix uninitialised**. One sighting, from the `premain-hang` bench era; needs a second
before theorising.
🔧 Hardened on the way past (libphoenix `c996bec`): `_file_init()` never checked its three
`calloc()`s and dereferenced them immediately — one failure was an instant NULL-deref that took the
other two streams with it. Each standard stream now goes through one checked helper.
